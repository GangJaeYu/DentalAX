# ② 확장 프롬프트 (실제로 입력한 단 하나의 프롬프트)

> [① 처음 아이디어](1-seed-prompt.md)를 구체화한 프롬프트입니다. **새 Claude Code 세션(Opus 5.5, effort high)에 이 내용 그대로 한 번 입력**했고,
> 이후 사람의 결정·개입 없이 약 1시간 45분 만에 서비스가 완성되었습니다. 자세한 과정: [BUILD_STORY.md](../BUILD_STORY.md)
>
> 직접 따라 해 보려면: 빈 폴더에서 Claude Code를 열고 아래 상자 안의 글을 통째로 붙여 넣으세요.

```text
치과 원내 업무 AX 웹 서비스: 처음부터 끝까지 완성해 주세요

0. 나와 이 작업에 대해
- 나는 코딩을 전혀 모르는 치과의사다. 내가 할 수 있는 일은 이 창에 짧게 답하기, 파일 더블클릭, 브라우저 열기 정도다.
- 이 작업의 목적은 Claude Code의 기본 능력만으로, 단일 프롬프트에서, 원내에서 바로 쓸 수 있는 완성 서비스를 만드는 것이다.

1. 반드시 지킬 규칙
- 외부 플러그인, 스킬, MCP 서버, 커넥터는 하나도 사용하지 않는다. 설치되어 있거나 목록에 보여도 호출하지 않는다. Claude Code 기본 도구(파일 읽기·쓰기·편집, 터미널, 코드 검색, 하위 에이전트, 웹 검색·웹 페이지 읽기)만 쓴다. 프로젝트 안에 설치하는 일반 라이브러리(npm/pip 패키지 등)는 사용해도 된다.
- 나에게 묻지 않는다. 결정할 일이 생기면 합리적인 기본값을 골라 docs/DECISIONS.md에 이유와 함께 적고 계속 진행한다. 단계가 끝날 때도 확인을 받으려고 멈추지 말고 마지막 단계까지 이어서 진행한다.
- 다음 행동은 하지 않는다: 유료 결제, 인터넷에 외부 배포, 이 폴더 밖 파일 수정, 시스템 전역 설정 변경. 이런 일이 필요하면 최종 보고에서 내가 할 일로 안내한다.
- LLM API 키가 없어도 전체 서비스를 설치·실행·테스트할 수 있어야 한다. 키가 없으면 AI 기능은 "데모 모드"(예시 응답)로 동작하고, 키를 넣으면 실제 AI로 동작한다.
- "완성"의 기준: 자동 테스트를 통과하고, 실제로 서버를 띄워 주요 화면과 흐름이 동작하는 것을 직접 확인한 상태. 확인하지 않은 것을 됐다고 보고하지 않는다. 테스트를 통과시키려고 테스트를 약하게 고치지 않는다.

2. 배경과 목표
치과 병의원에서 진료 외적인 업무를 AX(AI 전환)하려는 시도가 늘고 있다. 원내 서버(온프레미스)로 직접 AI를 돌릴 수도 있지만, 의료 민감정보나 환자 개인정보를 다루지 않는 업무라면 LLM API를 쓰는 편이 가성비가 좋아서 누구나 쉽게 원내 AX를 시작할 수 있다.
목표는 일반적인 치과 병의원 어디서나 쓸 수 있는 원내 업무 AX 웹 서비스다. 데스크 업무부터 행정, 서류, 사무, 재고까지 치과 운영 업무를 AI로 최대한 덜어 주는 것이 핵심이다.

3. 사용자와 운영 환경
- 사용자: 원장, 실장(데스크), 치과위생사, 간호조무사. 직원 5~20명 규모를 기준으로 한다.
- 원내 Windows PC 한 대가 서버 역할을 한다. 같은 원내 네트워크에 있는 PC, 태블릿, 휴대폰의 브라우저로 접속한다. 인터넷에 외부 공개하지 않는다.
- 비개발자가 README만 보고 30분 안에 설치할 수 있어야 한다. 매일 실행은 더블클릭 한 번(예: start.bat)으로 끝나야 한다.
- Node.js 같은 프로그램을 먼저 설치해야 한다면 README에 클릭 단위로 안내한다.

4. 개인정보 원칙 (가장 중요)
- 환자 정보를 저장하지 않는 구조로 설계한다. 환자 이름, 연락처, 주민등록번호, 차트번호, 진료·의료 정보를 담는 테이블이나 입력란을 만들지 않는다.
- AI로 보내는 모든 텍스트는 서버에서 먼저 개인정보 패턴을 검사한다(주민등록번호, 전화번호, 이메일, 카드·계좌번호 등). 감지되면 보내기 전에 막거나 가리고, 사용자에게 이유를 알려 준다.
- AI 입력창 근처에 "환자 개인정보 입력 금지" 안내를 눈에 띄게 둔다.
- 직원 정보는 업무에 꼭 필요한 최소한(이름, 역할, 근무 관련)만 저장한다.
- 개인정보보호법과 의료법(의료광고 규정 등)을 고려해서 설계하되, 서비스 안에 법률 자문을 대신하지 않는다는 점을 명시한다.

5. 기능 범위
아래는 출발점이다. 치과 현장에서 실제로 반복되고 시간을 많이 잡아먹는 일을 기준으로 직접 판단해서 다듬고 보완한다. 모듈마다 AI가 구체적으로 무엇을 돕는지 정한다.
- A. 데스크·소통: 공지·인수인계 보드, 오픈·마감 체크리스트, 전화 응대·일반 안내 스크립트 생성(진료시간, 주차, 보험 일반 안내 등), 온라인 리뷰 답글 초안, 안내 문자·안내문 문구 템플릿
- B. 재고·구매: 재료·소모품 목록, 입출고 기록, 적정 재고와 유효기간 알림, 거래처 관리, 발주서 자동 작성(인쇄·PDF), 단가 변동 기록, 엑셀(CSV) 가져오기·내보내기
- C. 행정·서류: AI 문서 작성기(공문, 안내문, 내부 규정, 업무 매뉴얼), 회의록 요약, 서식 보관함, 인쇄에 맞춘 문서 출력
- D. 인사·근무: 근무표, 연차·휴가 신청과 승인, 직원 교육 이수 기록, 신규 직원 온보딩 체크리스트
- E. 시설·법정 관리: 장비 점검·유지보수 이력, 멸균기 점검 기록(환자 정보 없이), 법정 정기 의무 일정 알림(방사선 장비 검사, 방사선 관계 종사자 교육과 선량 관리, 감염관리, 소방, 개인정보 교육, 의료폐기물 등). 주기가 확실하지 않으면 "확인 필요"로 표시하고 사용자가 고칠 수 있게 한다.
- F. 운영 지표: 지출 기록과 분류, 월별 요약 대시보드(환자와 연결된 매출 데이터는 제외)
- G. 원내 AI 도우미: 원내 매뉴얼·규정 문서를 올리면 그 내용을 바탕으로 질문에 답하고, 답의 근거가 된 문서를 함께 보여 준다.
- H. 관리: 사용자·권한, AI 설정(공급자, 모델, 키, 월 예산 한도), AI 사용량·비용 대시보드, 백업·복원, 활동 기록(감사 로그)
모든 기능을 얕게 만드는 것보다 핵심을 깊게 만드는 것이 낫다. docs/PLAN.md에서 필수(MVP)와 확장을 나누고, 필수는 반드시 완성한 뒤 확장까지 최대한 진행한다.

6. AI(LLM) 연동
- API 호출은 서버에서만 한다. API 키는 브라우저에 절대 노출하지 않고, 서버에 안전하게 저장한다.
- 공급자를 바꿀 수 있는 구조로 만든다. 최소한 Anthropic Claude와 OpenAI를 지원하고(가능하면 Google Gemini도), 데모 모드를 둔다.
- 기능별로 모델 등급을 설정할 수 있게 한다. 간단한 작업은 저렴한 모델, 긴 문서 작성은 상위 모델을 쓰는 식이다.
- 호출할 때마다 사용 토큰과 예상 비용을 기록한다. 월 예산을 넘으면 경고하거나 차단한다.
- 모델 이름과 가격은 작업 시점에 공식 문서를 웹 검색으로 확인해서 반영하고, 관리 화면에서 고칠 수 있게 한다.
- 시간 초과나 오류가 나면 쉬운 한국어로 안내한다.

7. 보안
- 로그인을 필수로 하고, 비밀번호는 안전하게 해시해서 저장한다. 역할별 권한(원장·관리자 / 실장 / 직원)을 둔다.
- 첫 실행 때 관리자 계정을 만드는 설정 화면을 띄운다. 기본 비밀번호를 코드에 박아 두지 않는다.
- 세션 만료, 로그인 시도 횟수 제한, CSRF·XSS·SQL 인젝션 방어, 입력값 검증, 보안 헤더를 적용한다.
- 누가 언제 무엇을 했는지 활동 기록을 남긴다.
- 하루 한 번 자동 백업하고 보관 개수를 정한다. 복원 기능도 만든다.
- 기본값은 원내 네트워크에서만 접속되게 한다. 외부 공개 시 위험과 주의사항은 README에 적는다.
- 의존성을 최소화하고, 알려진 취약점을 점검한다(npm audit 등).
- 완성 후 스스로 점검한 보안 체크리스트를 docs/SECURITY.md에 남긴다.

8. 디자인
- 원내에서 하루 종일 켜 두는 도구다. 눈이 편안하고, 정보 밀도가 적당하고, 클릭 수가 적어야 한다.
- 최신 SaaS 수준의 세련미를 갖춘다(Linear, Notion, Toss 같은 결). 깔끔한 여백, 일관된 컴포넌트, 부드러운 인터랙션을 원한다.
- 한국어 가독성이 좋은 폰트를 쓰되, 인터넷이 없어도 보이도록 프로젝트 안에 포함한다. 데스크톱과 태블릿 반응형, 라이트·다크 모드를 지원한다.
- 첫 화면은 대시보드로 한다. 오늘 할 일, 재고 경고, 다가오는 점검 일정, 공지가 한눈에 보여야 한다.
- 빈 화면, 로딩, 오류 상태까지 다듬는다. 키보드 조작과 색 대비 같은 기본 접근성을 지킨다.
- 가상의 치과로 만든 데모용 예시 데이터를 넣고, 실제 사용 전에 지울 수 있게 "초기화" 기능을 둔다.

9. 기술 선택 기준
기술 스택은 직접 결정한다. 기준은 다음과 같다.
- 비개발자가 설치하기 쉽고, Windows에서 안정적일 것
- 의존성이 적고, 오래 유지보수하기 쉬운 대중적인 기술일 것
- 데이터는 단일 파일 DB(SQLite 등)로 저장해서, 백업이 파일 복사로 끝날 것
선택 이유는 docs/DECISIONS.md에 적는다.

10. 진행 방식
작업을 단계로 나누고, 단계마다 구현 → 자동 테스트 → 실제 실행 확인 → 문제 수정 → PROGRESS.md 갱신 순서로 진행한다. 완료 기준을 채우지 못한 단계에서는 다음 단계로 넘어가지 않는다.
- 0단계 계획: docs/PLAN.md(기능 목록, 화면 목록, 데이터 구조, 단계별 완료 기준)와 docs/DECISIONS.md를 작성한다.
- 1단계 기반: 프로젝트 골격, DB, 로그인·권한, 공통 레이아웃과 디자인 시스템, 실행 스크립트를 만든다.
- 2단계~ 기능 모듈: 공통 규칙과 디자인 시스템을 먼저 고정한다. 그다음 서로 독립적인 모듈은 하위 에이전트로 병렬 작업해도 된다. 병렬 작업 결과를 합친 뒤에는 전체 테스트를 다시 돌린다.
- AI 마무리: 공급자 연동, 개인정보 필터, 비용 추적, 예산 한도를 완성한다.
- 최종 통합 검증:
  - 깨끗한 상태(새 DB)에서 README 절차대로 처음부터 설치·실행해 본다.
  - 전체 자동 테스트와 브라우저 E2E 테스트(로그인 → 모듈별 핵심 작업)를 돌린다.
  - 주요 화면 스크린샷을 찍어 직접 보고 디자인 일관성과 깨짐을 점검한다.
  - 보안 점검을 한다.
긴 작업 중에 맥락이 끊기더라도 PROGRESS.md만 읽으면 이어서 작업할 수 있게 기록한다.

11. 코드 주석
- 모든 파일 맨 위에 "이 파일이 하는 일"을 한국어로 요약한다.
- 주요 함수와 복잡한 부분에는 비개발자도 흐름을 따라갈 수 있게 쉬운 한국어로 무엇을 하는지, 왜 그렇게 하는지 적는다.

13. 완성 후 추천과 비용 분석 (docs/COST.md)
- 공급자·모델 비교표: 작업 시점의 공식 가격, 확인한 날짜, 출처 링크를 함께 적는다.
- 이 서비스의 기능별로 1회 평균 토큰을 추정하고, 소형(직원 5명)·중형(10명)·대형(20명) 치과의 월 예상 비용을 원화로 계산한다. 적용한 환율 같은 가정은 명시한다.
```
